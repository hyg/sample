p2pnet / v1

p2pnode：不用服务器的 P2P 节点

节点各自处在不同局域网、出口有 NAT。用 DHT 公布公网地址、用 STUN 探测映射、 UDP 打洞直连，连接建立后消息不经过任何服务器。DHT 上只写 IP:port， 内容端到端加密，长度定长分桶，时间加抖动与掩护流量。

Node.js ≥ 18 · 零第三方依赖 Kademlia / BEP-5 兼容 X25519 + AES-256-GCM 固定 64/256/1024/4096 桶长

01三条链路，各管一件事

把"找得到"和"连得上"彻底分开，是这个设计成立的前提。

发现 · DHT

标准 announce_peer / get_peers：把自己观测到的公网 IP:port 登记到一个由「网络名 + 时间轮次」派生的主题下，其他人查同一主题即可取得地址列表。只写地址，不写身份、不写内容。

探测 · STUN

仅用于开洞之前问一句"我出去后长什么样"。四台 STUN 并行探测，比对映射端口是否随目标变化， 判定 NAT 是锥形还是对称型，并据此生成候选端口。

通信 · 直连 UDP

双方同时向对方的候选地址发 16 字节探测包；收到即向包的真实来源回包。 洞打通后立刻握手、协商密钥，此后所有数据只在两端之间流动。

02一条消息的生命周期

1
算主题
topic = SHA1("p2pnet/v1/topic/" + network + "|" + epoch)， 每小时换一次，跨轮次时同时查上一轮。同一个网络名必然算出同一主题，别人猜到主题也只知道"有谁在关心它"。
2
收敛到最近的 K 个节点
迭代查询：每轮向"当前已知离主题最近的 K=8 个节点"中尚未访问的 α=3 个发 get_peers，把返回的节点并入候选集，直到最近 K 个都问过。 公告集与查询集必须收敛到同一批节点，否则两端互相看不见——这是最容易写错的一步。
3
公告 + 发现
向这批节点 announce_peer（最多 3 个候选端口）， 同时 get_peers 取回别人的 IP:port，再与本地 peer store 合并。
4
双向打洞
对每个候选地址每 400ms 发一个 16 字节探测包。收到包就向真实来源回包—— 对称 NAT 下公告的端口不成立，但它发来的包的真实源端口成立。
5
双向同时握手
双方各自发 192 字节 HELLO（临时 X25519 + 长期 Ed25519 + 签名 + 网络口令 HMAC）， 收到对端 HELLO 即完成，无需区分发起方。临时密钥提供前向保密，签名绑定身份。
6
加密传输
消息切片 → 填入固定桶长 → AES-256-GCM。 ACK 逐片确认，超时指数退避重传。空闲时发 PING 保活，并按随机间隔发掩护帧。

03谁知道了什么

"最小知情范围"落到每一方，边界如下。

角色能知道不能知道
公共 DHT 节点 某个 IP:port 对某个 160bit 主题感兴趣；公告的端口号；报文到达时间 消息内容、身份公钥、peerId、在线状态、对端是谁
STUN 服务器 你的出口 IP:port（这是它的唯一职责） 你在和谁通信、内容、身份
路径上的网络设备 两端 IP、报文长度（只有四种）、发送时刻 内容、真实长度（填充掩盖）、精确发送时刻（抖动 + 掩护帧）
对端节点 你的出口 IP、消息内容（这是通信的必要条件） 你的内网地址、你的其它会话
网络外扫描者 你的 UDP 端口存在 连握手都过不了：缺网络口令算不出 HMAC，无法建立会话
需要说清楚的诚实边界：DHT 只能做到"不写内容"，做不到"不暴露地址"。 任何人知道 network 名，都能在 DHT 上查到"有哪些 IP:port 在关心这个主题"。 要隐藏这一点，需要叠加 VPN / Tor 这类网络层手段——那已超出本程序的范围。

05能力与边界

能做到

锥形 NAT（含端口保持型）之间直连；单侧对称 NAT 与锥形 NAT 之间通常也能通； 40% 丢包下消息完整送达；跨轮次主题自动兼容；零服务端代码部署。

做不到

对称 NAT ↔ 对称 NAT。这是 NAT 的物理限制，任何"不用中继"的方案都不成立。 程序的处理是明确失败，不会偷偷降级到某台服务器——否则就违背了"通信不使用服务器"这条约束。
